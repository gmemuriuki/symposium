# Important flows

This section describes the logic of each `cargo agents` command.

## Crate-sourced skill resolution

A plugin loads a crate as a plugin by naming that crate in a `[[plugins]]` chained reference (`source.cargo = "..."`); the user can also load one directly by enabling the dependency it lives in (see [enablement](#dependency-enablement) below). When the owning plugin is active and the edge's predicates hold, the crate is resolved into the **active plugin set** — the shared list every facet (skills, MCP servers, hooks, subcommands) resolves over, so a crate-sourced plugin's extensions dispatch exactly like a registry plugin's. A single path handles every crate — a crate is always a first-class plugin, whether it describes itself with a `Symposium.toml`, with `[package.metadata.symposium]`, with both, or with neither:

1. `plugins::active_plugins` seeds a worklist from the trust-root plugins the registry loaded: each active plugin's `plugin.chained` edges whose predicates hold (evaluated against the *owning* plugin's provenance) contribute a `source.cargo` crate id.
2. For each request the fixed-point calls `pms.load_plugin(request, update)` on the **package-manager set** `active_plugins` was handed (built once per invocation by `Symposium::workspace`). An enabled dependency enters the worklist as its admitted handle, so equal coordinates with different supplier keys remain distinct through loading. A new `[[plugins]]` edge or a non-dependency named by `use` instead enters as an unresolved coordinate. Core sends the former back to its supplier as `PackageLoadTarget::Resolved` and the latter as `Coordinate`; it never reconstructs an exact request by looking up a coordinate. A hook that reused durable dependency coordinates lazily refreshes and admits that supplier's dependency snapshot before creating the exact requests, because keys are intentionally never persisted.
   - `CargoPm::fetch` resolves the source via `RustCrateFetch`. A workspace dependency is served from the source `cargo metadata` already extracted (path overrides for local path deps). Any other crate is read under `UpdateLevel::None` from cargo's extracted registry sources with no process and no network, and goes through the Cargo probe under `Check` or `Fetch`. Every route produces the same `PackageResolution`: an exact coordinate, a payload-free source classification, and Cargo's opaque package identity as the session key.
   - `CargoPm::plugin_from_fetched` returns that resolution with the crate as an unvalidated plugin, with a manifest the cargo PM's `manifest::merge` builds by layering two sources (merge order: `[package.metadata.symposium]` from `Cargo.toml` → `Symposium.toml` file). Both use the ordinary plugin-manifest schema and are parsed **leniently** (a malformed layer is logged and dropped).
   - The core Cargo instance admits the resolution with built-in authority, then validates it (`plugins::validate_plugin` with `PluginKind::Package`) under `ManifestOrigin::Crate`. The result is a `Plugin` whose `canonical` id is the resolved crate and whose private admitted content retains the session identity, classification, core authority, and canonical root. A configured replacement PM named `cargo` follows the same wire shape but receives remote authority.
3. `record_active` honors the crate plugin's own plugin-level predicates, appends it to the active set, and **enqueues its own `[[plugins]]` edges**. An `activated` set keyed on `(PackageHandle, validated plugin name)` collapses diamonds and breaks cycles without conflating two supplier resolutions that share a coordinate. The key is inserted only after the plugin gate passes, so a rejected route cannot suppress a later valid route; an already-activated identity skips both output insertion and edge expansion immediately.
4. Facet extraction then walks the active set. `collect_skills` runs each plugin's skill groups through the ordinary `load_skills_for_group` pipeline — honoring named groups, group predicates, and `source.path`/`source.git`. Discovery retains the lexical bundle path for installation while reading and hashing the final canonical `SKILL.md`. A path-sourced skill carries package authority only when that final file remains inside the admitted package root; escaped paths and every detached Git group remain unnamed by package authority. Git skill sources are fetched here, hence the `update` level. MCP-server filtering (`sync`), hook dispatch (`hook::dispatch_plugin_hooks`), and subcommand lookup (`subcommand_dispatch`) each iterate the same set. A crate plugin's **custom predicate definitions** are the one facet still not wired in — they resolve only from configured registries, and `warn_undispatched_crate_features` notes when a crate declares one.

A skill's install identity is the hash of its on-disk `SKILL.md` path, so a crate reached two ways dedupes to one install. The edge's version requirement is recorded but not yet enforced — the crate resolves against the workspace (pin / path override).

The key code paths are in `symposium-pm-cargo` (`CargoPm::load_plugin`, `plugin_from_fetched`, `manifest::merge`), `pm/mod.rs` (`PmInstance`, `PluginKind`), `plugins.rs` (`validate_plugin`, `ManifestOrigin::Crate`, `Plugin::canonical`), `plugins.rs` (`active_plugins`, `record_active`, `plugin_key`), `skills.rs` (`collect_skills`, `hash_origin_key`), and, in `symposium-pm-cargo`, `metadata.rs` (`symposium_metadata`), `workspace.rs` (`WorkspaceDeps`, `WorkspaceCrate`), and `sources.rs` (`RustCrateFetch`).

## Dependency enablement

A dependency's own plugin content — a `Symposium.toml`, `[package.metadata.symposium]`, or a `skills/` directory — is reachable without any manifest pointing at it, but only with the user's consent: dependencies are not a trust root.

1. `discovery::discover` asks the **untrusted** ecosystem transports (cargo, and any `[[package-manager]]`) for the plugins embedded in the workspace's dependencies. Core admits each supplier's complete dependency listing transactionally, then projects the exact matching `PackageResolution`s back to that supplier's `active_plugins` operation; predicates still consume only `PackageId`. `CargoPm::active_plugins` inspects each exact dependency in the source `cargo metadata` already extracted, with no probe or network, so two packages with equal coordinates but different opaque Cargo identities cannot be silently interchanged. The trusted registries are skipped because their plugins are trust roots and never need consent. Each candidate is classified against `[plugins]` on its coordinate: enabled by `use`, auto-enabled, declined, or an undecided candidate.
2. At sync time, `plugins::active_plugins` asks `discovery::enabled_dependencies` which dependencies `[plugins] auto-enable` or an applicable `use` entry covers. Every selected dependency contributes its exact admitted handle to the worklist, including every distinct package when two dependencies share a coordinate. A `use`d package that is not in the dependency snapshot contributes an unresolved coordinate instead. Both forms follow the same fixed point, so `pms.load_plugin` still honors the package's manifest sources, skill groups, and its own `[[plugins]]` edges. This reads config rather than the offer list, so `cargo agents use <crate>` loads a crate from crates.io whether or not the workspace depends on it, and even before its source has been fetched. (`CargoPm::search` is what lets `use` name such a crate.) The `use` entries are resolved by `discovery::Names`: a bare name means a registry plugin of that name, else a dependency of that name, else the package an ecosystem package manager has (`PmInstance::find`) at the level crate loading uses. `sync` resolves at `Check`, reading the cargo cache first and searching crates.io only for a crate that is not cached; the per-invocation paths resolve at `None`, which reads only dependencies and what is on disk. Matches from two package managers leave the name ambiguous, and it enables nothing; a name no package manager has is skipped.
3. Independently, a registry plugin with no dependency gate anywhere loads *dormant* (`PluginManifest::requires_use`) and activates only when a `use` entry names it. The gate rides the `PredicateContext` (`with_used` / `is_used`), so skill resolution, hook dispatch, subcommand lookup, help, and MCP filtering all agree.

Decisions are recorded by the consent prompt in an interactive `cargo agents sync` (`discovery::prompt_for_consent`, which writes `auto-enable` and `disable`) and by `cargo agents use` (`use` entries); `cargo agents status` reports what `[plugins]` currently decides. A hook never prompts: `SessionStart` names the pending candidates as context instead.

The key code paths are in `discovery.rs`, `config.rs` (`PluginsConfig`, `UseEntry`), `symposium-pm-cargo` (`CargoPm::active_plugins`, `CargoPm::load_plugin`), `plugins.rs` (`PluginManifest::requires_use`), `predicate.rs` (`PredicateContext::is_used`), and `plugins.rs` (`active_plugins`, `record_active`); bare names resolve in `discovery.rs` (`Names`, `used`).

## Help rendering

`cargo agents --help` (and `-h`, the bare `help` keyword, or no subcommand) is rendered by `help_render`, not by clap's default help.

1. The binary and the test harness parse argv with `Cli::try_parse_from`, then call `help_render::help_text(parse, args, sym, cwd)`. Because the decision happens after parsing, argument order (`--help --quiet`) does not matter and there is no second argv parser to keep in sync.
2. For no subcommand, `--help`/`-h`, or the bare `help` keyword, `help_text` returns the top-level grouped help: `render` slices clap's own rendered help (header + options block) and hand-renders "Commands for humans" / "Commands for agents" between them, mixing built-ins (`cli::builtin_audience`) with workspace-filtered plugin subcommands (`subcommand_dispatch::applicable_subcommands`).
3. For `<built-in> --help`, `help_text` re-renders clap's per-command help by walking clap's command tree to the named subcommand — so required-arg commands (`crate-info`), required-subcommand groups (`plugin`), and nested commands (`plugin list`) all work even though clap's auto help flag is disabled.
4. A plugin-vended `<name> --help` is left alone: `help_text` returns `None`, and dispatch forwards `--help` to the child binary, which owns its own help.

clap's auto help flag and help subcommand are disabled in `cli::Cli`; `--help`/`-h` is a manual `global` bool. The key code paths are in `help_render.rs` (`help_text`, `render`, `subcommand_help`), `cli.rs` (`builtin_audience`, the `Cli` flags), and `bin/cargo-agents.rs` plus `symposium-testlib` (the parse-then-`help_text` wiring).

## Subcommand dispatch

When the user runs `cargo agents <name>` for a name not built into the binary, clap's `allow_external_subcommands` routes it to `Commands::External(argv)`.

1. The binary (or library `cli::run`) calls `subcommand_dispatch::dispatch_external(sym, cwd, argv)`, which first resolves the **active plugin set** (`plugins::active_plugins` — registry plugins plus crate-sourced ones) so a crate's subcommands are dispatchable too.
2. `find_subcommand` walks that set. For each plugin it applies the plugin-level `depends-on` predicate against the workspace, then looks up `argv[0]` in `plugin.subcommands`. If the entry has its own `depends-on` predicate, that must also match. Two or more matches → error.
3. The matched subcommand's `command` field names an `Installation` on the same plugin. `installation::resolve_runnable` acquires the source if any, runs `install_commands`, and picks the `Runnable` (`Exec` for binaries, `Script` for shell scripts).
4. The child is spawned with stdio inherited. Its exit code is collapsed to a `u8` — the binary wraps it in `ExitCode::from`; the library treats non-zero as an error so the test harness can assert on success/failure.

The key code paths are in `subcommand_dispatch.rs`, `cli.rs` (the `External` arm), and `bin/cargo-agents.rs` (binary-side wrapping that surfaces the numeric exit code to the OS).

## Explicit plugin enablement

`cargo agents use` resolves registry plugins first, then workspace dependencies. For a name neither offers, it calls `PmInstance::find` on the ecosystem transports selected by `--pm`: a cached package is checked before search. As before, explicit `use` permits a search after a cache miss (`UpdateLevel::Check`), independently of the update level passed to the subsequent sync. Unselected transports are not queried in this fallback. The resolved canonical identity is recorded in `[plugins] use`.
